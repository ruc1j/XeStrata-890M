## 段階 1：調査

### 進め方

- 読み手 5 つ（変更の一覧、環境変数の突き合わせ、H1、H2 と H3、H4〜H6）が両方の木を読み、6 つ目が「890M 版に同等のものがない」「890M で効きそう」という主張をコードで確かめ直した（読むだけ、ビルドと GPU は使っていない）。結果の JSON は `~/workspace/bench/rdna3/survey.json`。

- 890M の prefill の内訳は、データフォルダーの records/2026-10-31-issues56-58.md にある 15K prompt（15,235 トークン）の STRATA_PREFILL_TIMING を使った: GPU 53,517 ms のうち qsa select 387 ms（0.7%）、qsa attn 7,014 ms（13.1%）、hc read 5,689 ms（10.6%。別の回の分割では up 2.9%、mix 3.4%）、hc write 2,066 ms（3.9%）、gemm gate/up 22.9%、gemm down 10.5%、gdn 13.0%。この記録は 10-31 のエンジンのもので、32K までの内訳は段階 1 の 5 で取り直す。

### 仮説の結論

- H1（SELECT_WMMA が一番の候補で、890M 版はスカラーの scorer に落ちている）: 一部だけ正しい。890M 版の qsa_select.cpp が行列演算を使っていないのは正しい。ただしスカラーの warp kernel ではなく、FP32 の SIMT のタイル GEMM（block_scores_simt、2 クエリ × 4 ヘッド × 4 ブロックを 1 work-item で）が既定。選択は 15K の prefill の 0.7%（scorer と top-k の合計）で、rdna3 の gfx1150 のコミュニティの計測（bench/results/2026-10-07-community-gfx1150/README.md:106）でも 1〜7K で差がなかった。「一番の候補」は外れ。decode は 1 クエリの warp kernel（qsa_block_scores）で、この scorer は通らない。
- H2（PA_FAST と HC_UPMIX は 890M 版にない）: 正しい。どちらもない。効果は PA_FAST が 15K で 1.5〜2%（文脈とともに増える）、HC_UPMIX が 1〜1.5% と見積もった。
- H3（ランタイムのホストブロックの mlock は 890M でも効く可能性がある）: 一部だけ正しい。890M 版が固定しているのは expert cache、PLE の表、lock_resident だけ。ランタイムのブロックがこの機で同じ形（/dev/zero (deleted)）で現れるかは、動いているエンジンの /proc/PID/maps で確かめる必要がある。890M でこの停止を見たことはない。
   - 確かめた（2026-11-18 03:40、計測中のエンジン r3all の /proc/PID/maps）: `/dev/zero` のマップは 0 個。GPU から見えるホストメモリーは `/dev/dri/renderD128` の rw-s のマップ 591 個（5,740 MiB）と `/dev/kfd` の 2 個で、rdna3 の掃き出しが探す「4 GiB 以下の /dev/zero (deleted) の共有マップ」はこの機の SYCL（HIP の adapter、ROCm 7.2）にはない。VmLck は 34,624,000 kB（expert cache の mlock）、VmSwap は 0。rdna3 の変更をそのまま移しても何も固定しないので、移植の候補から外した。renderD128 のマップは DRM の BO で、ユーザーのページを登録する userptr とは違う。
- H4（起動回数を減らすものは graph なので効かない）: 正しい。MEGAKERNEL は 1 GPU で 0.0 ms/窓（rdna3 の b253c7ced）、DRAFT_ALL は差なし（582da3f8e）で、ROUTE_PUBLISH と MULTICOPY は 890M 版に既にある。
- H5（CPU の分担、複数 GPU、KFD のキュー停止は関係ない）: 正しい。KFDQ は 8 本を超えるキューを持つカードのアイドルの電力の話、COMBINE_CPU は CPU でエキスパートを計算する場合だけ、WAIT_FUSE は resident graph でない経路だけ。
- H6（rdna_mmvq.cu と rdna_gr.cu は native_mmvq.cpp と fused_gr.cpp で同等以上）: ほぼ正しい。DPP の xor の和、sudot4、1 行 1 wave、gate と up の組、Q8 の HC の読みは揃っている。890M 版にないのは、窓の列ごとに重みをほどき直さない形（rdna_mmvq.cu:52-60）と、int8 の活性化での HC の読み（A8）。前者は帯域で決まる 890M では小さいと見た。展開や先読みの形（STRATA_MMVQ_RPS）は 2026-10-13 に測って差がなかった（docs/DETAILS.md:154）。

## 結論

| 候補 | ブランチ | prefill（3,461〜30,153 トークン） | decode | 答え | 勧め |
| --- | --- | --- | --- | --- | --- |
| PA_FAST | rdna3-port/pa-fast | 2.4〜3.2% 速い（3 回とも） | 会話 6 つでは揺れの中。長い文書の要約のあとは答えによって −9〜+11%（8 つの文書の 7 つで幾何平均 +1.7%） | 要約の言い回しが変わる | 既定にしてよい（decode が文書によって揺れることを承知のうえで） |
| SELECT_WMMA | rdna3-port/select-wmma | 揺れの中 | 揺れの中 | 8K と 30K で言い回しが変わる | opt-in のまま（既定にしない） |
| HC_UPMIX | rdna3-port/hc-upmix | 1.7〜3.2% 速い（3 回とも、8K の 1 回は測り直して確かめた） | 揺れの中 | 変わらない | 既定にしてよい |

- 両方を on にすると、prefill は 3,461〜30,153 トークンで 3 回とも 3.9〜5.0% 速い（計測 B）。2 つの効き目はほぼ足し算になる。
- PA_FAST は答えの言い回しを変えるので、そのあとの MTP の受理も文書によって上下する。DETAILS の 3 つの長さでは 512 トークンで 1.3〜9.0% 遅く、ほかの 7 つの文書では平均で 1.7% 速かった。
- SELECT_WMMA は、scorer だけなら 8K で 1.39 倍だが、選択は prefill の 1% に満たず、全体には出なかった。H1 の「一番の候補」は外れ。docs/XE.md の「入れなかった変更」に書く形で残す。
- 答えが変わった所は、どれも同じ要約の言い回しの違いで、内容の誤りはなかった。

## 移植しなかったもの

- HC_WN4（gr_write_norm_rs を 16 バイトの読み書きに）: 見込みが 0.4% ほどで、890M 版の write-norm は xn16_lo と xq8 も書くので、形が rdna3 と違う。
- ランタイムのホストブロックの mlock: 890M の SYCL には rdna3 が探す /dev/zero の共有マップがない（H3）。
- PF_F16 系: 890M のモデルの IQ2_S / IQ2_XXS / IQ1_M には専用のコードブックが要り、手間が L。780M では 4K で差がなかった。
- gfx1151 の decode の切り替え、MMVQ の列ごとのデコード: decode は帯域と GPU 待ちで決まり、見込みが小さい（H4〜H6）。
